## Contradictions between notes

1. **"Insert(Len, x) appends in place" is stale (wrong on WE main).**
   - Says in-place / recommends it: 02 §11 sketch (`// Insert(Len, x): in-place append`), 06 Synthesis ("Note `Insert(Len, x)` appends in place (memory)"), 05 §E.2 and 04 "Concrete API ideas" (recommend `Insert(Len, x)`).
   - Correct: 01 §8 and 07 #6 — since #1177 `Insert(Len)` calls `Append`; both cost ~220–250 µs and ~700–830 KB per 1,000 one-by-one sends (rows 8, 14). The memory note this came from predates #1177.

2. **Sort key: notes disagree, and some keys break after restore.**
   - 03 §11: stable sort by due only; "append order is already deterministic"; add a key "only if a sender iterates a Go map".
   - 06: `(Due, Seq)`; "Source adds nothing if Seq is per-queue and producers run in registration order".
   - 02: `(Due, Target, Seq)`; Seq "deterministic because producers run in fixed registration order".
   - 05: `(due, target, kind, source, seq)`. 04: `(due, priority, target, source, seq)`. 07: `(due, sender system index, per-tick seq)`, auto-assigned. 01: `(due, source key, seq)`.
   - Conflict with verified fact (row 7): a sender that loops over a search appends in row order, and row order differs live vs restored. So a Seq stamped at send time is not restore-stable. 03's and 06's "append order / per-queue Seq is enough" is wrong for any sender that iterates a search. A key needs stable fields (target ID, source ID — IDs are restore-stable, row 6) before Seq.

3. **Seq scope and width.** 02/04/07 bench use `uint32`; 06 uses `uint64` and makes Seq the cancel handle (never reused). 07 says "per-tick seq". A per-tick Seq repeats across ticks, so two delayed requests with the same due tick from different send ticks can tie → key not total, which undercuts 07's own "unique Seq lets an unstable sort be deterministic".

4. **Stable vs unstable sort.** 07 recommends `slices.SortFunc` (unstable) with a unique Seq. 06 and 01 recommend stable sort (06: "Append + stable sort is simplest and FIFO-preserving"). `immutable.Slice` only offers stable sort (row 9), so 07's path needs a copy out to a plain `[]T`. Not a factual conflict, but the notes point two ways.

5. **"No engine has a cap on chains/drains" is too broad.**
   - 05 Verdict: "Every same-tick drain loop I read … loops until empty with no cap"; 05 §E.4 and 02 §11.6: no depth cap anywhere.
   - But 03 (Mass `MaxIterations = 5` per flush, row 25) and 06 (Doom 3 `MAX_EVENTSPERFRAME 4096` hard error, row 28; Netty 100,000 per tick, row 32) show global per-drain caps. Correct statement: no engine has a *per-request chain depth* field; several have *per-drain count* caps.

6. **"No game engine gives per-request cancel handles" (06 top finding 4) contradicts 06's own Unreal section and 05.**
   - 06 §Unreal: `FTimerHandle` + `ClearTimer` / `PauseTimer` per handle (row not separately checked; Epic page via fetch tool). 05 §D: GoWorld `CancelTimer(tid)` (V). 06 §Netty: `Timeout.cancel()` (row 32 source). Only the narrower 06 "Could not find" line is right: Doom 3 and Source *delayed event queues* cancel by scan, not by handle.

7. **Event service point.** The design fires delayed events at tick start. 06 notes Doom 3 and Source service *after* thinks (row 28, 29) and calls start-of-tick "fine"; 03 §11 says Mass's off-graph firing is "a known source of order surprises". No conflict on facts, but no surveyed engine fires at tick start — it is Cardinal's own choice, not prior art.

8. **Bench numbers differ between 01 and 07** (01: ~220–239 µs, 701 KB, 51 KB batched, SortStableFunc 105 µs; 07: ~250 µs, 832 KB, 59 KB batched, 131 µs). Explained by request size (01: 32 B; 07: 48 B) and 07 counting `SliceOf` build in the sort. Not a contradiction, but quote one set, with its struct size.

9. **Link/version nits.** 03's Mass links use branch `main`; the repo's branch is `master` (raw URLs 404 on `main`). 02 cites `flecs.h` line ~362; the define is at 367. 06 cites Go `master`; I checked Go 1.25.5 (same text).
